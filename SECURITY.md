# Security

- **Login flood trade-off (accepted):** while one address floods logins with made-up user names, the account's real user name answers "wrong username or password" (401) where the made-up names get "too many attempts" (429), so that flooder can learn the user name. This keeps a flood from locking the owner out; the password is still required, and guesses at it are throttled on their own.
- **Known-device cookie:** every successful login sets a signed, httpOnly `tastearr_device` cookie (one year; it stops working when the password changes). It grants nothing by itself, but a login from that browser gets its own throttle entry and password-check slot, so a flood naming the real user from many addresses can't refuse the owner there. A browser that has never logged in can still be refused during such a flood.
- **Full throttle table (accepted):** when the login throttle table is full (10,000 entries), the oldest entries are evicted instead of refusing new clients, so the owner is never refused because of it. An attacker with roughly 900+ addresses could evict entries, their own included, and restart their back-off; known-device browsers are unaffected.
